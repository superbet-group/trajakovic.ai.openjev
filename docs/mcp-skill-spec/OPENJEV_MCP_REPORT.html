Summary

OpenJev answers typed questions about a piece of text (a "state") with probabilities. The MCP server wraps the OpenJev HTTP API so that agents such as Claude Code can call it as tools. Revision 1.2 makes it compliant with MCP 2026-07-28 and adds the Playground batch features (many states, one question set) as first-class tools.

Three things changed from 1.1. First, the protocol target is MCP 2026-07-28 (stateless, server/discover, per-request _meta), with a fallback for older clients that send initialize. Second, batch moved from phase 3 to phase 2, because it is client orchestration over the existing API (one request per state) and needs no server change. Third, a new no-network tool, batch_results, queries, exports and compares finished batch outputs.

Words like MUST, SHOULD and MAY are used in the RFC 2119 sense, as in the spec. Terms are explained in the glossary.

Architecture

Requests flow top to bottom: a client talks JSON-RPC over stdio to the MCP server, the server validates and dispatches to a tool, and the tool calls the OpenJev HTTP API, which runs the model. Hover or focus a box to light up its connections and read what it does.

Batching deep dive

OpenJev batches on two axes only: questions per request (1 to 256) and images per request (0 to 8). It takes exactly one state per request. So "batch many states" is client orchestration: the MCP batch tool sends one request per state, with bounded concurrency, and writes every row to a JSONL file that is the resumable source of truth.

Select a stage.

Three kinds of "batching"

  • Questions per request (server-native): the server splits 1 to 256 questions into canvas chunks. Call this server canvas chunking. It never batches states.
  • States per call (client): batch sends one POST /v1/systemone per state. filter instead packs many small items into one state.
  • Client pagination (cursor): one MCP call reads at most max_items_per_call rows and returns next_cursor. This splits a long job across calls.

The cursor loop

The cursor is an opaque token the client passes back. It is a tool argument, not MCP protocol pagination. If a call is cancelled and no result comes back, the client calls again without a cursor and with resume: true: the server scans the output file and skips finished ids.

Key rules

  • Rows are written in input order through a reorder buffer, so output is deterministic for any concurrency (1 to 4, default 1).
  • A 429, 503 or 529 closes a shared cooldown for every worker and drops effective concurrency to 1. A row still overloaded after its retries stops the call with stopped_reason: backpressure; it is not recorded as an error.
  • MLX serialises reads on one thread, so concurrency above 1 gives no speedup there (lint warning W405). vLLM admits up to 64 reads.
  • Review queue: rows with choice p_top below 0.8, noul probability in the grey band 0.15 to 0.85, or a wide score spread. A seeded 3 percent audit sample of auto-accepted rows is chosen by sha256(seed, id), so it is reproducible.
  • dry_run makes no network call. It returns the import report, three preview states, the exact first HTTP body and an estimate.
  • Exports (CSV, Markdown, ojui-batch) are created new only, inside the allowed roots. batch_results can export, sort, filter and compare any finished file without spending a single read.
